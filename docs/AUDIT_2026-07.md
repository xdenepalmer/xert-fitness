## Fixed in this pass

See commit history. All three were reproduced before fixing; the two SQL defects were reproduced against PostgreSQL 16.

1. **Class cancellation refunded zero credits** (critical) — `admin_cancel_class_session` read `status` from an UPDATE's `RETURNING`, which yields the post-update value, so the refund filter never matched. Members permanently lost credits whenever staff cancelled a class. Proven: 5 credits before, 5 after cancelling 3 credit-backed bookings; correct is 8.
2. **Account deletion was impossible** (critical) — five audit tables combine `on delete set null` to `auth.users` with an unconditional immutability trigger. Postgres implements SET NULL as an UPDATE, which the trigger aborted, so `deleteUser()` failed for any member who had ever booked a class. Broken feature and an APP 11.2 exposure.
3. **CSV formula injection** (high) — untrusted public-form text reached admin exports unescaped. Quoting is not a defence because CSV parsing strips quotes before the spreadsheet evaluates the cell.
4. **One deleted member could take the whole store's checkout offline** (critical) — `orders.user_id` is `on delete set null`, so a deleted buyer leaves the order with a NULL user. `fulfill_stripe_checkout` rejected that on `user_id is distinct from`, the event landed in the ledger as `failed`, and `api/checkout.js` gates every purchase on there being zero failed fulfilment events. Result: a permanent 503 for every member, unrecoverable because the order's user id can never be restored. Reachable by an ordinary sequence, since Stripe redelivers webhooks for up to three days: member pays, credits granted, member deletes account, Stripe redelivers, checkout dies. Verified against PostgreSQL 16 that the fix settles the redelivery while still rejecting a wrong product, wrong amount or wrong user.
5. **A roll-call correction charged a second credit** (high) — `admin_set_booking_status` treats any move into `confirmed` from outside `('requested','confirmed')` as taking a new place. `attended`/`no_show` are only reachable *from* `confirmed`, so they already hold an unrefunded credit; flipping back charged again. Ordinary front-desk behaviour triggers it: staff mark people in as they arrive, before start time, then fix a mis-tap. Verified against PostgreSQL 16 — 9 credits became 8 on a correction that should cost nothing.
6. **`npm test` executed nothing** — the script resolved the `test` directory as a module on Node 22, which CI pins. The suite was healthy; the invocation was not.

## Verified, not yet fixed

### Standalone schema files have drifted from the migrations (high)

`src/supabase/booking_schema.sql` is documented in the README as an operator apply step and its own header says "Safe to re-run". It unconditionally drops and recreates `member_announcements_select_live_or_admin` **without** the `audience`/`member_announcement_targets` predicate that `supabase/migrations/20260714015000` added — the file contains no occurrence of `audience` at all. Re-running it downgrades the policy so every member can read other members' private targeted notices. `src/supabase/announcement_archival_upgrade.sql` carries the same stale policy.

The root cause is structural: two parallel SQL trees (`supabase/migrations/` and `src/supabase/`) are maintained by hand. Recommend making `supabase/migrations/` authoritative and generating or retiring the second tree; failing that, add a test asserting the hardened predicate appears in **every** file that creates the policy, not just the newest.

### REFUTED

- **"Supabase anon key is inlined into the public bundle"** — this is by design. The anon/publishable key is meant to ship to browsers; RLS is the security boundary, and `resolvePublicSupabaseConfig` already validates that it is an anon rather than service key. Not a defect.
